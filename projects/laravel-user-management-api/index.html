Laravel User Management API

A Laravel 12 REST API with a Vue 3 and Inertia admin dashboard. It's a small CRUD, but it's built the way I build client APIs: each concern in one place, one error format, and explicit rules for who can do what.

The problem

The task was a simple user-management CRUD. Even a simple CRUD has to answer the questions every business application does: who is allowed to manage records, what the API sends back when input is wrong, what happens when someone deletes a record and later adds it again, and how the list behaves once it grows past one page.

What I built

  • A REST API under /api/users with list, create, show, update and delete, plus paginated search on name and email.
  • Token authentication for API clients: POST /api/auth/token issues a Sanctum bearer token, and POST /api/auth/logout revokes it.
  • An admin dashboard (Laravel Breeze, Inertia.js and Vue 3) that calls the same API, maps 422 validation errors onto the matching form fields, and debounces search.
  • Separate tables for the people who log in (backend_users) and the records being managed (users).
  • Roles and permissions (users.view, users.create, users.update, users.delete) seeded for an admin role, with a UserPolicy registered against the model.
  • Soft deletes, with a restore path when a deleted email is created again.

Architecture

Each layer has one job, so a change to validation, business rules or the response shape touches one file:

Route (auth:sanctum)
  → Api\UserController        HTTP in, HTTP out
  → StoreUserRequest          validation, 422 on failure
  → UserService               business rules (create or restore)
  → UserRepositoryInterface   bound to UserRepository (Eloquent)
  → UserResource              response shape

The frontend mirrors this. Dashboard.vue uses a useUsers composable for state and actions, which calls a small userService.js wrapper around Axios. Components under Components/Crud only render.

Important engineering decisions

Admins and managed users are different tables

The people who sign in to the dashboard live in backend_users, which the auth guards and password broker point at. The records being managed live in users. Keeping them apart means a managed record can never sign in by accident, and the CRUD can't edit an administrator's credentials.

One validation error format

API requests extend an abstract ApiFormRequest that overrides failedValidation(), so every validation failure returns 422 with {"message": "Validation failed", "errors": {...}}. The dashboard relies on that shape to put each message under the right field.

Re-creating a deleted user restores it

The email column has a unique index, and soft-deleted rows still hold their email. Validation ignores soft-deleted rows, and UserService::create() checks for a trashed record with the same email first: if there is one, it restores it, fills the new values, stamps restored_at and returns 200 with "User reactivated". Otherwise it creates a new record and returns 201. The client can tell the two outcomes apart, and the database constraint is never hit.

The repository sits behind an interface

AppServiceProvider binds UserRepositoryInterface to the Eloquent implementation. The service depends only on the interface, so the query logic can change, or be faked in a test, without touching business rules.

Testing and static analysis

The repository includes Breeze's feature tests for authentication, registration, password reset, email verification and profile updates. PHPStan runs at level 8 with Larastan over app and routes, and Laravel Pint handles formatting. A Postman collection covers the API and saves the issued token automatically.

The API endpoints themselves don't have feature tests yet. They're the next thing to add: validation errors, the restore path, pagination and token revocation.

Performance considerations

  • The list endpoint is paginated (10 per page by default) and ordered by newest first.
  • Search runs LIKE '%term%' across first name, last name and email. A migration adds indexes on first_name and last_name, but a pattern with a leading wildcard can't use a B-tree index to seek, so the database still scans. That's fine at this size. For a large table I'd switch to prefix matching or a full-text index.
  • per_page comes straight from the query string, so it should be capped before this goes anywhere near production.

What I'd change next

The UserPolicy and permissions are in place, but the API controller doesn't call them yet, so any valid token can perform every action. Enforcing the policy in each controller action, and adding the API feature tests above, are the two changes that would make this production-ready.
