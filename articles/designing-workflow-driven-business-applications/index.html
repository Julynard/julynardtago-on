Case study, business workflow systems

Designing workflow-driven business applications with Laravel

The systems that mattered most to their users weren't CRUD screens. They were processes: an expense moving through approvals, a payment being matched against a ledger, a ticket moving from sold to used. This is how I design them.

By Julynard Tago-on, Laravel / PHP Full-Stack Engineer. Published 6 October 2026.

The three systems below belong to a government agency, a CoreProc client and a freelance client, and their code is private. This article describes the shape of each problem and the design approach, not their code or internal details. The code sample is an illustrative sketch written for this article.

Three workflows

Project-expense approvals at DOST-PCIEERD

At DOST-PCIEERD I automated the project-expense approval workflow in the agency's Laravel project management system, which cut approval processing time by 60%. I also built project timeline tracking that flags overdue milestones; deadline tracking was 90% accurate across the project portfolio. Separately, I rebuilt search across more than 1,000 approved projects, cutting search time by 70%.

Payments reconciliation at CoreProc

At CoreProc I led delivery of a payments reconciliation system from setup to production, and wrote 97 of its 107 commits. It matches transactions from three sources: PayMaya, kiosk cash files delivered over SFTP, and mobile-app transactions. Imports run on a schedule, and CI quality gates guard every change.

Ticketing at Dinoland

For Dinoland, a dinosaur-themed attraction, I designed and built a ticket management system in Laravel and jQuery covering ticket status tracking, purchase orders, revenue reports and a user activity audit trail.

An approval chain, a reconciliation run and a ticket lifecycle look different, but they have the same skeleton: records move through states, specific people are allowed to move them, time matters, and someone will later ask "who did this, and when?"

1. Write the process down before the schema

The most expensive workflow bugs are disagreements about the process, not code mistakes. Before writing a migration I want a short spec that answers:

  • What states can a record be in, and which are final?
  • Which transitions are allowed, and who can trigger each one?
  • What must happen on each transition: notifications, totals, records in other tables?
  • What happens with time: what becomes overdue, what runs nightly, what expires?
  • What does the business need to see afterwards: reports, history, exceptions?

This is the habit I brought to the multi-tenant field-sales platform at CoreProc, where I set the planning standard by writing design specs, implementation plans and QA test plans before coding. It was also a core part of my role at CloudTech ERP, where I turned client finance requirements into technical specifications and acted as the link between business users and the development team.

2. Make the states explicit

A workflow whose state is spread across nullable columns (approved_at, rejected_by, is_paid) has impossible combinations waiting to happen. I give each workflow record a single status column backed by a PHP enum, and keep the list of allowed transitions next to it.

3. Put each transition in one place

Every transition should go through one class or method that checks the current state, checks permission, writes the change and its consequences in a database transaction, and records history. Controllers, Nova actions, console commands and queued jobs all call that one entry point, so the rules can't be skipped by coming in through a different door.

// Illustrative sketch, not client code.
enum ExpenseStatus: string
{
    case Submitted = 'submitted';
    case Approved = 'approved';
    case Rejected = 'rejected';

    public function canMoveTo(self $next): bool
    {
        return $this === self::Submitted
            && in_array($next, [self::Approved, self::Rejected], true);
    }
}

final class ApproveExpense
{
    public function __invoke(Expense $expense, User $approver): Expense
    {
        Gate::forUser($approver)->authorize('approve', $expense);

        if (! $expense->status->canMoveTo(ExpenseStatus::Approved)) {
            throw new InvalidTransition($expense->status, ExpenseStatus::Approved);
        }

        return DB::transaction(function () use ($expense, $approver) {
            $from = $expense->status;

            $expense->update(['status' => ExpenseStatus::Approved]);
            $expense->history()->create([
                'from' => $from,
                'to' => ExpenseStatus::Approved,
                'user_id' => $approver->id,
            ]);

            ExpenseApproved::dispatch($expense);

            return $expense;
        });
    }
}

Notifications go out through an event after the state change, so a failed email doesn't roll back an approval. In production I'd also make sure the event's listeners run after the transaction commits.

4. Permissions belong to transitions, not screens

"Can this person open the expense page?" and "can this person approve this expense?" are different questions. The second depends on the record: its amount, its project, whether the approver submitted it. Policies are the right place for that, and every transition calls one, whichever interface it was triggered from.

5. Time is an input

Workflows change state without anyone clicking. Milestones become overdue, kiosk files arrive overnight, unpaid orders expire. In Laravel these are scheduled commands, and two rules keep them dependable:

  • Make them safe to re-run. An import that runs twice, or a job retried after a timeout, shouldn't create duplicates. Upserting on the source system's transaction reference is the simplest guard.
  • Make them observable. Record what each run imported, matched and skipped, so "did last night's file arrive?" has an answer that doesn't need a developer.

6. Reconciliation is a workflow too

A reconciliation system doesn't prove that everything matched. Its job is to show the exceptions clearly. Every transaction from every source ends up matched, missing from one side, or mismatched on amount or date, and the people who resolve exceptions need their own states: under review, resolved, written off. Designing the exception workflow as carefully as the matching logic is what makes the system useful to a finance team.

7. Keep an audit trail from day one

Someone will eventually ask who changed a ticket, approved a payment or edited a purchase order. A history table written inside the same transaction as the change (who, what, from which state, to which state, when) answers that cheaply. Adding one after an incident means the history before it is gone for good.

Checklist

  • States, transitions and roles agreed in a written spec before the schema.
  • One status column backed by an enum, with allowed transitions next to it.
  • One entry point per transition: permission check, state check, transaction, history.
  • Side effects through events, dispatched after commit.
  • Scheduled jobs that are safe to re-run and leave a record of each run.
  • An exception workflow for anything that can't be processed automatically.
  • Feature tests for each transition, including the ones that should be refused.
