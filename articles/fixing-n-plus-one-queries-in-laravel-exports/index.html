Fixing N+1 queries and timeouts in Laravel exports

On a multi-tenant field-sales platform at CoreProc, I eliminated N+1 queries across 26 BI export processors and resolved export timeouts by moving the work onto queued, chunked jobs. This is how I find and fix that kind of problem.

By Julynard Tago-on, Laravel / PHP Full-Stack Engineer. Published 6 October 2026.

The platform's code is private, and I don't have before-and-after timings from it that I can publish, so there are no benchmark numbers here. The code samples are illustrative, with invented model names, not client code.

The situation

The platform holds per-tenant activity data for field sales teams at a multinational FMCG client, and exports it every night to S3 for Power BI. There were 26 export processors, and as the data grew, exports started timing out. I eliminated the N+1 queries across all 26 processors and moved the long-running exports onto queued, chunked jobs.

Why exports are where N+1 hides

Export code nearly always loops over rows and reads a relationship or two for each one. With Eloquent's lazy loading, each of those reads is a separate query:

// Illustrative. One query for the orders, then more for every row.
$orders = Order::query()
    ->whereBetween('created_at', [$from, $to])
    ->get();

foreach ($orders as $order) {
    $writer->addRow([
        $order->customer->name,          // 1 query per row
        $order->branch->region->name,    // 2 more per row
        $order->items->sum('quantity'),  // and another
    ]);
}

With 20 rows in a local database this is instant. With a tenant's full history it's tens of thousands of queries in one process. Exports also run at night, when nobody is watching the slow query log.

Finding them

  • Make lazy loading fail outside production. One line in AppServiceProvider::boot() turns every accidental lazy load into an exception in local and CI runs: 
    Model::preventLazyLoading(! app()->isProduction());
  • Count the queries per run. Wrapping an export in DB::enableQueryLog(), or counting with DB::listen(), shows straight away whether the count grows with the number of rows. It should stay flat.
  • Look for repeated SQL. The same statement with only the ID changing, hundreds of times, is the signature of an N+1.

Fixing the queries

The fix is to load each relationship once for the whole set, and to ask the database for aggregates instead of loading collections to count in PHP:

// Illustrative. A fixed number of queries, whatever the row count.
Order::query()
    ->whereBetween('created_at', [$from, $to])
    ->with(['customer:id,name', 'branch:id,region_id', 'branch.region:id,name'])
    ->withSum('items', 'quantity')
    ->chunkById(1000, function ($orders) use ($writer) {
        foreach ($orders as $order) {
            $writer->addRow([
                $order->customer->name,
                $order->branch->region->name,
                $order->items_sum_quantity,
            ]);
        }
    });
  • with() loads each relationship in one WHERE IN query per chunk.
  • Column lists such as customer:id,name keep the loaded models small. The foreign key has to be in the list, or the relationship can't be matched.
  • withSum() and withCount() push aggregation into SQL.
  • chunkById() pages by primary key, so memory stays flat. Unlike offset-based chunk(), it doesn't skip rows if the data changes during the run.

Fixing the timeouts

Removing N+1 queries makes each export much cheaper, but a large tenant's export can still outlast a single process's time limit. That's why the second half of the fix was structural: queued, chunked jobs.

  • Split the export. Instead of one long process, dispatch a job per chunk (by ID range or by date range) and combine the parts at the end. Laravel's job batching gives a completion callback for the combine step.
  • Carry context explicitly. In a multi-tenant system each job needs its tenant passed in, never taken from global state left over from a previous job.
  • Stream the output. Write rows to a file or stream as you go and upload it, rather than building the whole export in memory.
  • Set limits deliberately. A job's $timeout should be shorter than the queue connection's retry_after, or a slow job can be picked up twice. Horizon shows which jobs are slow or failing.

Don't forget the indexes

Eager loading moves the work into WHERE id IN (...) queries on foreign keys, and date-range filters need an index on the date column. Running EXPLAIN on the queries an export actually issues is the quickest way to spot a full table scan.

Indexes have limits worth knowing. In my public Laravel User Management API, search uses LIKE '%term%' on indexed name columns. Because the pattern starts with a wildcard, MySQL can't use those indexes to seek. At that project's size it doesn't matter; on a large table, prefix matching or a full-text index would.

Measure, then measure again

For each export I want three numbers before and after a change: query count, duration and peak memory. Logging them on every run turns "the exports feel slow" into a trend you can watch, and shows quickly when a new column brings an N+1 back.

Checklist

  • Model::preventLazyLoading() enabled outside production.
  • Query count per export independent of row count.
  • Relationships eager-loaded with column lists; aggregates done in SQL.
  • chunkById() or lazyById() instead of get() for large sets.
  • Long exports split into queued jobs with explicit tenant context.
  • Job timeouts below the queue's retry_after.
  • Indexes checked with EXPLAIN on the real queries.
  • Query count, duration and memory logged per run.
