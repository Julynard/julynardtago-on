Building a maintainable Laravel API

What "maintainable" means in practice, using the code of my Laravel User Management API: where each concern lives, why, and what I'd still change.

By Julynard Tago-on, Laravel / PHP Full-Stack Engineer. Published 6 October 2026.

Every snippet here is taken, lightly trimmed, from a public repository, Julynard/technical-task-simple-user-management-crud, a Laravel 12 API with a Vue 3 and Inertia dashboard. It's small, which makes the structure easy to see. The same structure is what keeps much larger client APIs workable.

The test I use for "maintainable"

Pick a likely change and count the files it touches. Changing an error message, adding a validation rule, changing what happens on create, renaming a response field: in a maintainable API each of those is one file, and the file is obvious from its name. When a change means editing a controller, a model and a Vue component at once, the boundaries are in the wrong place.

Controllers only translate HTTP

The controller reads the request, calls the service, and picks a status code and response. It holds no business rules and no queries:

public function store(StoreUserRequest $request): JsonResponse
{
    $result = $this->users->create($request->validated());

    if ($result['restored']) {
        return response()->json([
            'success' => true,
            'message' => 'User reactivated successfully',
            'data' => UserResource::make($result['user']),
        ], 200);
    }

    return response()->json([
        'success' => true,
        'message' => 'User created successfully',
        'data' => UserResource::make($result['user']),
    ], 201);
}

Type-hinting StoreUserRequest means validation has already passed by the time this method runs, so the controller never handles invalid input.

Validation fails the same way everywhere

API clients shouldn't need to special-case each endpoint's errors. Every API request class extends one abstract base that fixes the failure response:

abstract class ApiFormRequest extends FormRequest
{
    protected function failedValidation(Validator $validator): void
    {
        throw new HttpResponseException(
            response()->json([
                'message' => 'Validation failed',
                'errors' => $validator->errors(),
            ], 422)
        );
    }
}

The Vue dashboard depends on that contract. Its service wrapper turns any 422 into { message, errors }, and the form puts each message under the field it belongs to. Adding a new field means adding a rule; the error handling already works.

Business rules live in a service

The one real business rule here is what to do when someone creates a user whose email belongs to a soft-deleted record. The email column has a unique index and soft-deleted rows keep their email, so a plain insert would fail at the database. The service restores the old record instead:

public function create(array $data): array
{
    $trashedUser = $this->users->findTrashedByEmail($data['email']);

    if ($trashedUser) {
        $trashedUser->restore();
        $trashedUser->fill($data);
        $trashedUser->setAttribute('restored_at', now());
        $trashedUser->save();

        return ['user' => $trashedUser, 'restored' => true];
    }

    return ['user' => $this->users->create($data), 'restored' => false];
}

The validation rule matches it, ignoring soft-deleted rows when it checks uniqueness (unique:users,email,NULL,id,deleted_at,NULL). Rule and behaviour agree, and the client sees the difference as 201 Created or 200 with "reactivated".

Restore, fill and save are three writes. If restoring were part of a longer process, with an audit entry or a notification, I'd wrap the steps in DB::transaction() so a failure halfway leaves nothing behind.

Queries live in a repository behind an interface

Search and pagination are in UserRepository, and AppServiceProvider binds the interface to it:

$this->app->bind(UserRepositoryInterface::class, UserRepository::class);

Whether a repository layer earns its place on top of Eloquent is a fair debate. For a single model it's arguably extra ceremony. What it buys is one place for query logic. When search changes from LIKE to full-text, or a tenant scope gets added, the service and controller don't move.

The response shape is its own layer

UserResource lists every field the API returns. Adding a column to the table doesn't silently add it to the API, and renaming a field for clients doesn't mean renaming the database column.

Authentication: two kinds of client

The API has two kinds of caller. The dashboard runs in the browser with a Breeze session. Postman, or any other API client, uses a bearer token from POST /api/auth/token, which checks the credentials against backend_users and returns a Sanctum personal access token. POST /api/auth/logout deletes only the token in use, so signing out one client doesn't sign out the others.

Admins (backend_users) and the managed records (users) are separate tables. A managed record has no password and can't sign in, and the CRUD can't touch admin credentials.

Authorization: the gap I'd close first

The pieces are there: spatie/laravel-permission defines users.view, users.create, users.update and users.delete, the admin role gets all four, and a UserPolicy checks them. But the API controller never calls the policy, so any valid token can do everything. Authentication is enforced; authorization isn't yet.

The fix is small. Add an authorize() method to each Form Request, or call Gate::authorize('update', $user) in each controller action, and back it with a feature test per permission. I'd rather say this plainly than have a reviewer find it.

Tests and static analysis

PHPStan runs at level 8 with Larastan, which catches most type mistakes before runtime, and Pint keeps formatting out of code review. The feature tests are Breeze's tests for the session auth flows. The API endpoints need their own tests: validation failures return the documented shape, the restore path returns 200, pagination respects per_page, and a revoked token stops working.

What carries over to larger systems

  • Decide the error contract first and enforce it in one base class.
  • Keep business rules out of controllers, even when there's only one rule.
  • Make the response shape explicit with API Resources.
  • Make validation agree with database constraints; soft deletes and unique indexes are where they usually drift apart.
  • Treat authorization as a separate step from authentication, and test it.
